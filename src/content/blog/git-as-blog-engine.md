很多人把"写博客"和"部署博客"当成两件事：先在编辑器里码字，再点一下"发布"按钮。但当你的博客是一个 Git 仓库时，这两件事会自然地合并成同一件事——**每一次写作，都是一次提交**。

这篇文章想说的不是"怎么部署"（那是工具文档的事），而是**为什么应该把博客当成一个可追溯的工程来管理**。

## 写作即提交

当文章本身就是仓库里的一个 `.md` 文件，你的写作历史就和代码历史共用同一套机制：

```bash
git commit -m "post: 新增《用 Git 把博客变成可追溯的工程》"
```

这条提交里包含的不只是文字，还有它的诞生时刻、上下文，以及你在它之前改过的所有东西。半年后回看，你看到的不是一篇冷冰冰的文章，而是它一路长成的轨迹。

## 用分支管理"草稿态"

公开站点只跑 `main` 分支，但我习惯把未完成的文章放在 `draft` 分支：

```bash
git checkout -b draft/next-post
# 写一半，随时提交，不用担心泄露
git checkout main
```

等文章真正写好，再合并进 `main` 触发部署。分支让"写了一半"和"已发布"在物理上分开，既安全又清爽。

## 部署只是提交的副作用

我选择 Vercel + GitHub 的组合，核心原因只有一个：**push 即部署**。

```text
git push origin main
        │
        ▼
GitHub 收到推送
        │
        ▼
Vercel 拉取、构建、上线
```

我不需要记住任何部署步骤，因为部署已经被"提交"这个动作完全吸收了。少一个需要记住的流程，就少一个会出错的环节。

## 回滚比备份更优雅

传统博客的"备份"是另一份拷贝，平时基本不看，真出事时还不一定能还原。Git 的回滚则是原地的、精确的：

```bash
git revert <commit-hash>   # 撤销某次发布，并留下撤销记录
```

你不需要另存一份，因为历史本身就是备份。

## 元数据也是代码

文章的标题、日期、封面图，我全部写在 frontmatter 里，和正文一起进版本库：

```yaml
---
title: '用 Git 把博客变成可追溯的工程'
pubDate: '2026-08-05'
heroImage: '../../assets/blog-placeholder-5.jpg'
---
```

这意味着"这篇文章什么时候发的、配的什么图"不再是某个后台数据库里的黑盒，而是**可以 grep、可以 diff、可以 review** 的明文。

## 结语

把博客当成工程来管理，短期看是多了一层 Git 的学习成本，长期看却是把"发布"从一个让人紧张的动作，变成了像保存文件一样自然的习惯。

当你不再害怕发布，你才会写得更多。
